# Nimaz data console — extraction, interconnection, and delivery to existing installs

Date: 2026-07-28
Status: approved, in implementation

Three problems, one design. The `nz` data console currently lives inside the Android repo
as `nimaz-data/`, with its sources gitignored and no path to the app at all. This spec moves
it into its own private repo, defines how a promoted artifact reaches the Gradle build, and
— the part nothing has solved until now — defines how a content correction reaches a device
that already has Nimaz installed.

---

## 0. Where the problem actually is

`app/src/main/assets/database/nimaz_prepopulated.db` is 147 MB, tracked through Git LFS, and
copied onto a device by Room's `createFromAsset` — which runs **only on fresh install**. That
single fact drives most of this document:

- Correcting the asset reaches new installs and nobody else. `docs/ARCHITECTURE.md` §9 records
  this as the reason the 16-line Mushaf data and the 15 translations ship as seeded JSON rather
  than baked into the asset.
- Every content fix that *did* go into the asset cost another whole 140 MB LFS object. LFS
  stores each version entire; no delta applies. The Nimaz `.git` is 576 MB, of which
  **508 MB is `.git/lfs`** holding 11 objects.
- There is exactly one precedent for repairing an existing install:
  `HadithBackfillSeeder`, which applies a bundled JSON patch to 379 hadiths that shipped with
  empty text. It is hand-written, per-table, and nothing proves the patch matches the asset.

The console already computes row-level key-set diffs, deterministic artifact hashes and a
per-collection manifest. The delivery mechanism this spec adds is therefore **derived from the
build, not hand-authored** — which is the difference between a fix that is correct and a fix
that is believed to be correct.

## 1. Two repos

### `arshad-shah/nimaz-data` — private, fresh init, single commit

```
docs/DESIGN.md                  was Nimaz docs/nimaz-data-console.md
README.md
pyproject.toml
nimaz_data/                     core/ changes/ rules/ build/ cli/ ui/ agent/ import/
tests/
data/
  console.yaml                  schema-wide policy: user tables, splits, keys, protected
  schema.sql                    generated by `nz init`; committed
  genesis.json  keys/*.txt.gz   written once; committed
  collections/<name>/           collection.yaml + records.ndjson   (~125 MB, committed)
  changes/  changes/applied/
  rules/*.py
  importers/*.py                new — §4
upstream/                       was nimaz-pro-data/ minus output/
  json/  sources/  scripts/  audio/  *.md
vault/  .build/  out/           gitignored
.github/workflows/checks.yml release.yml
```

Four things change as paths shift to the root:

| | |
|---|---|
| `docs/nimaz-data-console.md` | becomes `docs/DESIGN.md`; a three-line stub stays in Nimaz |
| `.github/workflows/nimaz_data_checks.yml` | drops `paths:` and `working-directory:` — both existed only because it was a subdirectory |
| `.gitignore` | loses the `data/collections/*/`, `data/keys/`, `data/genesis.json`, `data/schema.sql` lines. In a dedicated repo those are the deliverable, not scratch |
| Nimaz `CLAUDE.md` | the data map says the console lives in its own repo |

**Sources are committed.** 125 MB of NDJSON, largest single file
`tafseer.ibn_kathir_en/records.ndjson` at 38.5 MB — under GitHub's 100 MB hard limit, text,
no LFS. This is the whole point of the tool: a one-row correction reads as
`1 insertion(+), 1 deletion(-)` instead of `Bin 147292160 -> 147292160 bytes`. A repo that
cannot rebuild itself from its own contents is not a source of truth.

**`upstream/json/` moves too** (171 MB across 53 files). It is the input the importers read,
and keeping it is what lets the corpus be re-derived rather than merely trusted.

**`nimaz-pro-data/output/nimaz_prepopulated.db` is deleted, not moved.** It carries 379
hadiths with empty `text_arabic`/`text_english` that neither the JSON sources nor the shipped
asset have. It is stale, damaged output, and the next person to regenerate from it ships those
blanks. Deleting it also drops a 140 MB LFS object.

### Nimaz — the app, and the integration only

Keeps: `data.lock.json`, the Gradle fetch task, `ContentPatchSeeder`, doc stubs. Loses:
`nimaz-data/`, `nimaz-pro-data/`, `app/src/main/assets/database/`, and the LFS rule in
`.gitattributes`.

## 2. Genesis is published, not merely archived

The sealed vault — the currently shipped asset, sha256 `6b57b4d4…`, 147,292,160 bytes,
`user_version = 12` — is published as release **`data-v1`**.

This is load-bearing. CI needs a fixed baseline to verify the content patch against
(§5), and the alternative — reconstructing genesis from committed sources — stops working the
moment `nz change fold` replays changes into those sources. Publishing genesis once gives
every future build an immutable reference that no local state can drift from.

The vault still goes to cold storage: `vault/corpus.db` + `corpus.sha256` on object-locked
object storage plus one offline copy. After genesis it is a witness, not a dependency — the
guard never opens it in normal operation (design §13, §15).

## 3. The release contract

`nz release` (§6) tags `data-vN` and publishes:

| asset | |
|---|---|
| `nimaz-<hash>.db` | the artifact |
| `build.json` | the receipt — artifact hash, per-collection version, hash, row count |
| `content-patch.json.gz` | genesis → this artifact, row-keyed (§5) |
| `seed-assets.tar.gz` | Mushaf layouts + translations (phase 8) |
| `SHA256SUMS` | |

`build.json` is a receipt, not a network contract. It answers "which tafseer version is in app
build 812" with a lookup instead of an investigation.

## 4. `nz import` — and the property that makes it worth having

An adapter lives in `data/importers/<name>.py` and is discovered exactly like a rule:

```python
@importer(id="tr.bn.bengali", collection="tr.bn.bengali",
          source="upstream/json/translations/bn_bengali.json")
def bengali(ctx):
    for row in ctx.json():
        yield {"ayah_id": row["ayah"], "text": row["text"]}
```

The adapter yields records. **Core does everything that must be identical every time**: NFC
normalisation on the way in, schema coercion from `collection.yaml`, key sort, canonical NDJSON
encoding, and provenance stamped with the source file's sha256 plus a retrieval date.

Normalising here rather than on export is deliberate, and resolves deviation 2 in the current
README: normalising vocalised Arabic can reorder combining marks, and invariant 1 says the
corpus is never rewritten — not even to make a check pass. On import it is a declared choice;
on export it would be a silent edit.

**Import respects the write funnel.** A *new* collection writes sources directly. An
*existing* one emits a change directory with `expect{}` computed from the diff — so a
re-import that would silently drop 4,000 rows is refused at build stage 3 like any other
change. Invariant 3 holds: import gets no privileged path.

### The reproducibility gate

`nz import --all --check` re-runs every adapter into scratch space and byte-compares the result
against the committed sources, exiting non-zero on drift. It runs on every PR.

This converts a claim into a proof: the corpus is *derived from* `upstream/`, not hand-massaged
at some point in the past and no longer explicable. It is also what makes adding a translation
cheap — one `collection.yaml`, one adapter, one command.

## 5. Delivery to existing installs — the content patch

### The artifact

`nz patch emit` diffs the baseline artifact (the `data-v1` release asset) against the current
one and writes a keyed row patch:

```json
{
  "patchVersion": 3,
  "baseline": "sha256:6b57b4d4…",
  "target":   "sha256:3f9a…",
  "update": [
    { "table": "ayahs", "key": { "id": 1 },
      "set": { "text_uthmani": "…", "text_arabic": "…" } }
  ],
  "insert": [],
  "delete": []
}
```

Gzipped, bundled in the APK as `assets/database/content-patch.json.gz`.

### Three properties that make it safe rather than clever

**1. It cannot touch user data.** `console.yaml` already enumerates the 20 user tables —
bookmarks, khatam progress, prayer tracking, tasbih, zakat. The emitter refuses to produce an
op outside the 24 content collections, and the seeder refuses to apply one. The failure mode of
a blanket "re-copy the database on upgrade" — destroying user state — is structurally
unreachable here, not merely avoided by care.

**2. Cumulative from genesis, so the upgrade path does not matter.** Every op is an idempotent
keyed `UPDATE`/`INSERT OR REPLACE`. A user who installed at app v810 and one who installs today
converge on identical rows. There is no patch chain to order, no missed intermediate release,
and re-applying is harmless. The patch grows only as corrections accumulate; today it holds one
op.

**3. CI proves it.** `nz patch verify` downloads the `data-v1` asset, applies the patch to it,
recompiles, and asserts the result is **byte-identical** to the target artifact hash. Blocking.
A patch that does not reconstruct the artifact cannot ship. This is the check that
`HadithBackfillSeeder` never had.

### The Android side

`ContentPatchSeeder` generalises `HadithBackfillSeeder`, which becomes a special case of it and
can eventually be deleted. It reads the bundled gzip, compares `patchVersion` against a DataStore
key, applies every op inside one transaction against a table allow-list derived from the patch's
own declared content tables, then stores the version. It joins the existing startup seeder path
alongside Help, Dua, Qaida, Mushaf and translation seeding.

Fresh installs get the corrections already baked into the fetched artifact; the seeder sees a
`patchVersion` it has already recorded at build time and does nothing. Existing installs get the
patch applied on first launch after update.

The first thing it ships is real: `ayahs.text_uthmani` and `ayahs.text_arabic` both carry
`U+FEFF` at index 0 of ayah 1:1 — a byte-order mark inside the Bismillah — on every device
running Nimaz today.

## 6. `nz release` and `nz app sync`

`nz release --bump minor` is the pipeline as a single gate: doctor → build → validate → guard →
promote → patch emit → patch verify → tag → publish. It refuses on a dirty tree, on uncommitted
change directories, and on any blocking finding.

The point is not convenience. A nine-step runbook is a step you eventually skip, and the step
you skip is the one that would have caught the thing.

`nz app sync --repo ../Nimaz --tag data-v3` closes the loop: verifies every published asset
hash, writes `data.lock.json`, branches, and opens a PR whose body is the `build.json` receipt
plus a patch summary. The interconnection becomes a command rather than a habit.

## 7. Transport into the Gradle build

`data.lock.json` at the Nimaz root:

```json
{
  "repo": "arshad-shah/nimaz-data",
  "tag": "data-v1",
  "artifact": { "file": "nimaz-6b57b4d4.db", "sha256": "6b57b4d4…", "bytes": 147292160 },
  "patch":    { "file": "content-patch.json.gz", "sha256": "…", "version": 1 }
}
```

A Gradle task `fetchNimazData` resolves the release through the GitHub API, downloads each
asset, **verifies its sha256 before anything else touches it**, and caches under
`~/.gradle/caches/nimaz-data/<sha256>/`. The cache directory is registered as a generated assets
source root, so `createFromAsset("database/nimaz_prepopulated.db")` keeps working with **no
Kotlin change at all**.

Token resolution, in order: `NIMAZ_DATA_TOKEN` env → `nimazDataToken` Gradle property →
`gh auth token`. Failure prints what to set and where, not a stack trace.

The task is up-to-date when the verified file is already cached, so only a cold build pays the
140 MB. CI caches `~/.gradle/caches/nimaz-data` keyed on the lockfile hash.

**The trade being accepted:** a release build now needs network access and a token for a private
repo. In exchange the Nimaz repo stops carrying a 140 MB blob that grows by another whole copy
every time a single character changes.

## 8. Repo cleanup

Runs **last**, and only after the data repo is live, `data-v1` is published, and Nimaz builds
green from the fetched artifact.

1. Full mirror backup clone, kept until the rewrite is confirmed good.
2. `git filter-repo --path nimaz-pro-data --path app/src/main/assets/database
   --path app/src/main/assets/databases --invert-paths`
3. Drop the `*.db filter=lfs` rule from `.gitattributes`; delete `.git/lfs`.
4. Force-push; re-clone every working copy.

576 MB → roughly 30 MB. Every commit SHA changes: 32 remote branches are invalidated and any
open PR must be recreated.

**Known limitation, stated rather than glossed:** GitHub does not delete orphaned LFS objects
from remote storage on a force-push. Reclaiming the quota needs a support request or a
re-created repository. That is a follow-up, not something this sequence achieves.

## 9. The TUI — design §10, tiers L1–L4

L0 tokens exist. On top of them:

- **L1 primitives** — `Stack` `Row` `Box` `Text(role)` `Rule` `Icon` `Spacer`. No product meaning.
- **L2 elements** — `Panel` `Button` `Chip` `StateDot` `KeyHint` `Table` `ListRow` `Callout`
  `CodeBlock` `Stat` `Field`.
- **L3 patterns** — `MasterDetail` `CommandBar` `DiffView` `RecordInspector` `QueueList`
  `ProgressStages`.
- **L4 screens** — Doctor, Collections browser, Record inspector, Changes queue, Build runner,
  Rules report.

A lint test enforces the one-directional tier rule: a screen that names a colour or a spacing
value fails the suite. That test is the only thing that keeps a design system from decaying into
one-offs, which is why it is part of this spec and not a later nicety.

This is the largest item here by a wide margin. It is sequenced last and may be split into its
own spec rather than allowed to hold up the pipeline.

## 10. Sequence

| | | |
|---|---|---|
| P1 | New repo, bootstrap, sources committed, `data-v1` published, CI green | mechanical |
| P2 | `upstream/` moved; Nimaz stripped to app + integration; docs and CLAUDE.md | mechanical |
| P3 | `nz import` + adapters for the existing corpus + `--check` gate | engineering |
| P4 | `nz patch emit` / `patch verify`; `nz release`; `release.yml` | engineering |
| P5 | Nimaz `data.lock.json` + Gradle fetch task; LFS asset dropped | engineering |
| P6 | `ContentPatchSeeder` + tests; **the BOM fix ships to existing installs** | engineering |
| P7 | `nz app sync` | small |
| P8 | Quran seed assets become `nz` outputs | optional |
| P9 | TUI L1–L4 | large, splittable |
| P10 | History purge | destructive, last |

P6 is the payoff. It is the first time a content correction reaches a device that already has
the app. Everything before it is plumbing that makes P6 provable rather than hopeful.

| | |
|---|---|
| History | Fresh init, one commit. The five commits on `claude/nimaz-console-design-i6vysk` are not carried across. |
| Visibility | Private. The corpus is licensed third-party content; publishing it is a separate decision with licensing work attached. |
| Sources in git | Yes. 125 MB of NDJSON. |
| `nimaz-pro-data/output/` | Deleted. 379 blanked hadiths. |
| Artifact transport | Fetched from a GitHub Release, pinned by sha256. Not committed. |
| Existing installs | Derived content patch + one generic seeder, verified by artifact-hash reconstruction. |
| Full DB re-copy on upgrade | Rejected — the same file holds user data. |

## 12. Out of scope

- Migrating `HadithBackfillSeeder`'s existing fills into the patch format. It keeps working;
  folding it in is a later cleanup once `ContentPatchSeeder` has shipped and settled.
- Splitting `ayahs.text_tajweed` into a `tajweed.spans` collection (design §4). It is exactly the
  kind of change this tool exists for, but it is a schema change and belongs in its own pass.
- Reclaiming GitHub-side LFS storage quota (§8).
